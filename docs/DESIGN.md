# my-context 设计文档

> 状态：v0.1 草案（2026-10-29）

## 1. 目标

把一个人所有的关键个人信息集中存放在自己可控的地方（本地优先），并在与 AI 大模型对话时让 AI 按需读取这些信息，从而给出真正「了解你」的建议。

上下文范围举例：

- 基础生理：身高、体重、体检指标、作息习惯
- 财务：收入、储蓄、各银行卡、负债、持仓（股票/基金）、大额支出计划
- 职业：在职公司、岗位、技能、薪酬、职业意向
- 家庭与社会关系：父母状况、感情状态、重要亲友
- 偏好与原则：饮食口味、风险偏好、决策原则、长期目标

**非目标（现阶段）**：不做多人共享账户；不做自动抓取（爬网银/券商）；不做公网多租户服务。

## 2. 核心概念与数据模型

关键设计决策：**把「事实」与「记录」分开存**。

- **事实（Fact）**：结构性、会随时间变化的状态。如「身高 175cm」「就职于 X 公司」「持有 Y 股票 2000 股」。带生效时间区间，旧值保留历史。
- **记录（Entry）**：只追加的事件与叙事。如一次体检、一次谈话、一段日记、一次重要决策及其理由。永不修改，只追加。

### 2.1 模型

```
domain    主题域：health / wealth / career / family / relationship / preference / goal
entity    实体：我、某人（父母/伴侣）、某公司、某银行卡……（带可选主域；「我」在 init 时作为 self 种子实体创建，跨域）
fact      事实：entity + key + value(JSON) + domain(可空 → general) + valid_from/valid_to + source_entry_id + sensitivity
entry     记录：时间 + 类型(日记/事件/对话摘录/导入) + 标题 + Markdown 正文 + 关联实体 + 标签
embedding 向量：entry 的语义嵌入（M2 起）
audit_log 操作日志：时间 + 操作类型 + 对象 + 来源(AI/手动/导入/系统) + 摘要
```

示例：

- fact：entity=我, key=employer, value={"company":"X公司","title":"后端工程师"}, valid_from=2024-03, valid_to=2026-10
- fact：entity=招商银行尾号1234, key=account_type, value="储蓄卡", sensitivity=sensitive
- entry：2026-10-20「和爸妈视频，爸血压偏高，提醒他复查」

### 2.2 敏感分级（sensitivity）

- `normal`：可随任意对话注入（饮食偏好、职业方向）
- `sensitive`：仅当话题明确相关才注入（收入、健康异常、持仓明细）
- `secret`：默认永不注入，需用户在当次对话显式授权（卡号、具体存款数额）

## 3. 系统形态

本地优先的单机系统，一条核心链路：

```
SQLite(单文件) ←→ Rust 核心(存储/检索/注入策略) ←→ MCP Server ←→ AI 客户端(Claude/ZCode/…)
```

- **v1 不自建聊天 UI**：以 MCP server 接入现成 AI 客户端，最快跑通「AI 读取全部上下文」的核心价值。
- **v2 再做 Tauri + Vue 桌面端**：管理功能全量内聚（明细见 §7），后续加内置对话；复用 Miyo 已验证的模式。
- **云同步（可选，靠后）**：本地单文件库端到端加密后整体同步（私有对象存储 / WebDAV / 私有 Git 仓库），绝不以明文上云。

## 4. MCP 工具清单（v1）

读取：

- `get_context(query?, max_chars?)`：**注入总入口**——档案常驻 + 按话题检索相关历史，受字符预算约束（每轮对话调一次）
- `get_profile(domains?, include_sensitive?)`：纯档案摘要——各域当前有效事实的紧凑视图
- `search_entries(query, top_k)`：FTS5 trigram + 向量混合检索（RRF 融合、时间新近微加权、预算裁剪）
- `recent_entries(n)`：最近 n 条记录
- `get_monthly_report(year?, month?)`：月报材料——本月记录、待确认事实（超 6 个月未更新）、操作统计

写入（让「对话即采集」成立）：

- `add_entry(title, body, entity_ids?, tags?)`
- `upsert_fact(entity, key, value, sensitivity?)`：更新事实，旧值自动失效并保留历史
- `add_entity(name, kind, domain)`
- `delete_entry / delete_fact`：软删进回收站；彻底清除需 CLI 显式 `--purge`
- `archive_entity / merge_entities`：归档与合并（合并 v2 起）

注入策略（核心内实现，客户端无感）：

1. 每轮对话先注入「档案摘要」——全部 `normal` 事实，约 1–2KB（一个人一生的结构化事实其实很小，可以常驻）
2. AI 按话题调用 `search_entries` 拉取相关历史记录
3. `sensitive` 事实仅在话题相关时由 AI 显式拉取；`secret` 级需用户当次授权
4. 注入总量设预算上限（如 8K tokens），超限按 相关度 × 时间衰减 截断

## 5. 存储与检索选型

| 需求 | 选型 | 理由 |
|---|---|---|
| 主存储 | SQLite（sqlx） | 单文件、零运维、易备份/导出；团队已熟练 |
| 全文检索 | SQLite FTS5（trigram 分词） | 中文子串可用；<3 字符查询回退 LIKE |
| 语义检索 | embeddings 表 + Rust 暴力余弦 | 个人库千条量级足够，省掉 sqlite-vec 扩展加载；量大再换 |
| 嵌入模型 | 本地 Ollama（如 bge-m3，`MY_CONTEXT_EMBED_MODEL` 配置） | 隐私：嵌入计算不出本机；未配置则纯关键词检索 |

否决的备选：纯 Markdown 文件库（事实的时间版本化与一致性难维护，量大了检索差）；服务端多租户架构（隐私风险与运维成本，与「数据主权」目标冲突）。

## 6. 个人信息的管理

管理是围绕数据模型的层级展开的：**域（domain）→ 实体（entity）→ 事实/记录**，配套录入、查改删、一致性治理、审计、备份五套机制。

### 6.1 组织方式与日常操作

- 7 个固定主题域是一级导航；**实体是管理的基本单元**（「我」「父亲」「招商银行尾号1234」），点开实体 = 当前有效事实 + 关联记录时间线。
- 标签用于跨域主题聚合（如 `#2026跳槽` 同时挂在新公司事实与相关记录上）。
- 每条数据的生命周期状态：`active → stale(待确认) → archived / deleted`。archived 默认不注入不检索，可手动查看。

| 操作 | 规则 | v1 入口 | v2 入口 |
|---|---|---|---|
| 查 | 档案总览按域浏览、实体详情、时间线、全文/语义搜索 | CLI `list`；MCP `get_profile` / `search_entries` | 档案页 / 时间线页 |
| 增 | 见 6.2 录入渠道 | MCP `add_entry` / `upsert_fact`；CLI `add` | 表单 + 拖拽导入 |
| 改 | 见 6.3 修改规则 | MCP `upsert_fact` | 实体编辑表单 |
| 删 | 见 6.3 删除规则 | MCP `delete_*`；CLI `delete --purge` | 回收站页 |
| 归档 | 实体/域整体转 archived | CLI `archive` | 右键归档 |

### 6.2 录入

优先级（从省力到费力）：

1. **对话中顺带更新**（主力）：用户随口说「我跳槽去字节了」，AI 自动调用 `upsert_fact` + `add_entry` 落库
2. **结构化编辑**：桌面端表单（M3）
3. **批量导入**：思源笔记、聊天记录导出、体检报告 PDF（M3+）

### 6.3 修改与删除

- **改事实**：版本化覆盖——新值生效、旧值 `valid_to` 封口保留，永不原地改写历史；同一实体同一 key 允许多条历史共存。
- **改记录**：记录不可编辑。写错了就追加一条「更正记录」并关联原文，原文保留（像账本的 red-charge）。
- **删**：默认软删进回收站（保留 30 天可恢复）；「彻底清除」才物理删除记录/事实及对应向量、嵌入与导出缓存。`secret` 级数据的彻底清除立即执行、不留软删副本。

### 6.4 一致性治理与保鲜

- **冲突检测**：同一实体同一 key 出现多条同时有效的事实 → 进「待处理」队列，由用户裁决。
- **实体合并**：重复/重名实体（「招行卡」建了两次）支持合并，历史全部指向合并后的实体。
- **月度审查**（保鲜主机制）：每月让 AI 生成「上下文月报」——列出超期未确认的事实（`updated_at` 过旧自动标记 stale）、待处理冲突、当月记录摘要。
- 新事实覆盖旧值不等于删除：历史永远可查，这是「事实带时间区间」的直接推论。

### 6.5 审计与操作日志

- 新增 `audit_log` 表：时间、操作类型、对象、**来源**（AI 对话 / CLI 手动 / 导入 / 系统）、摘要。所有 MCP 与 CLI 写操作落日志，回答「这条事实是谁在什么时候、基于什么改的」。
- AI 的每次写操作同时记录触发它的对话 entry，语境可追溯。

### 6.6 备份与导出

- `export` 命令一键导出全库为 JSON + Markdown（数据主权兜底）
- 定期自动备份 SQLite 文件到本地多副本；敏感数据不做裸网盘同步

## 7. 桌面端功能设计（Tauri + Vue）

定位：**管理加速器 + 信任锚点**——所有涉及数据审查、编辑、清除的操作都在本地可视化完成；对话初期依赖外部 MCP 客户端，产品成熟后内聚为内置对话。

### 7.1 信息架构

左侧一级导航：`档案 / 时间线 / 审查中心 / 录入 / 回收站 / 审计日志 / 内置对话(M4) / 设置`，外加全局搜索（⌘K）与全局快速捕获（⌘N）。

### 7.2 页面功能明细

**档案总览（首页）**

- 按域分组的实体卡片墙：实体名、有效事实数、最近更新时间、新鲜度标记（stale 高亮）
- 「档案完整度」提示条：指出信息稀疏的域（如 wealth 仅 2 条事实），一键跳转快速录入
- 实体卡片右键：编辑 / 归档 / 合并 / 调整默认敏感级

**实体详情**

- 左栏：当前有效事实表（key / value / 更新时间 / 敏感级 / 来源入口），事实行点开看历史版本与新旧值 diff；操作：新增、编辑（版本化覆盖，提交前预览旧值→新值）、作废
- 右栏：该实体关联记录的时间线
- 实体级操作：归档、合并到其他实体（选目标 → 冲突预览 → 确认）

**时间线**

- 全部记录倒序流；过滤器：域 / 实体 / 类型 / 标签 / 时间范围 / 关键词
- 单条记录：Markdown 正文渲染、关联实体跳转、「追加更正记录」、软删

**录入**

- 快速捕获（⌘N 全局唤起）：单行输入，AI 判定落成事实更新还是独立记录（复用 M2 的对话抽取提示词）
- 表单新增：记录（标题 / 正文 / 标签 / 关联实体多选）
- 导入向导：思源笔记 / 聊天记录导出 / 体检报告 PDF；导入前预览解析结果、逐条指定归属实体与敏感级，确认后批量落库（审计来源=导入）

**审查中心**（治理主界面）

- 三个队列 Tab：待确认事实（stale）/ 待处理冲突 / 待合并实体
- 每项带 AI 预填的建议动作（如「该事实 8 个月未更新，建议确认或更新」），一键采纳或手动改写
- 月报：查看历史月报、手动触发本月生成

**回收站**

- 软删项列表带 30 天倒计时；恢复 / 彻底清除（二次确认；secret 级条目不回显内容）

**审计日志**

- 写操作流水：时间 / 操作 / 对象 / 来源 / 摘要；按来源与对象过滤；点开跳转触发它的对话语境或导入批次

**设置**

- 注入策略：token 预算、时间衰减参数、按域开关常驻注入
- 敏感级总览：全库事实按敏感级列表，支持批量调整
- 备份与导出：备份目录与频率、立即备份、导出 JSON / Markdown
- MCP 接入：显示本机 server 启动命令，一键复制 Claude / ZCode 的配置片段
- 对话后端（M4）：云端模型 API key 管理 / 本地 Ollama 地址
- 数据目录：显示库文件位置、支持迁移

**内置对话（M4）**

- 会话列表 + 对话区；系统层固定注入「档案摘要」；回答中引用的记录/事实带角标，点击跳转来源
- AI 写操作（更新事实 / 新增记录）在对话流中以**确认卡**呈现：采纳 / 撤销，不静默落库
- 模型切换：云端 / 本地 Ollama；涉及 secret 级事实的对话强制走本地

**全局搜索（⌘K）**：跨实体 / 记录 / 标签混合检索，结果分组直达。

### 7.3 桌面端与核心的关系

- 桌面端不直接写 SQLite，统一调用 Rust core API（与 MCP server 同一套），保证注入策略、敏感分级、审计行为在所有入口一致
- 技术栈与工程模式复用 Miyo 已验证的 Tauri 2 + Vue 3 + sqlx 迁移体系

## 8. 安全与隐私

- 本地库以 OS 磁盘加密（FileVault/BitLocker）为底，应用层对 `secret` 级字段再加密（可选 SQLCipher）
- 发往云端大模型的内容受注入策略约束：`secret` 级默认永不出机；若要求绝对不出网，可切换本地模型（Ollama）作为对话后端
- MCP server 只走本机 stdio，不开网络端口

## 9. 技术选型与理由

- **Rust 单仓库**（core + mcp + cli，后期加 tauri）：与既有栈一致，`rmcp` 官方 SDK 成熟
- **先 CLI + MCP，后 Tauri UI**：核心价值在数据与链路，UI 是管理加速器而非前置条件

### 8.1 代码结构（M1 已落地）

```
crates/core   存储与领域：db(连接/迁移) / repo(实体·事实·记录·审计) / profile(档案注入) / export(导出)
crates/mcp    rmcp stdio server：get_profile / search_entries / recent_entries / add_entry / upsert_fact / add_entity
crates/cli    my-context 二进制：init / add / list / export / serve
```

实现与 §2.1 的一处偏差：`domain` 放在事实而非实体上（实体主域可选）——「我」这一个实体的事实横跨所有域，按实体域分组会把全部事实挤进同一组。

## 10. 里程碑

- **M1 最小闭环**（已落地）：SQLite schema + 迁移；CLI（init/add/export）；MCP server（get_profile / search_entries / add_entry / upsert_fact）；接入 Claude/ZCode 完成一次真实对话
- **M2 检索与采集增强**（已落地）：FTS5 trigram + 向量混合检索（RRF + 预算裁剪）；get_context 注入总入口；server instructions 内置采集规则与敏感级指引；月报材料 get_monthly_report
- **M3 桌面端（管理）**：档案总览 / 实体详情 / 时间线 / 录入与导入 / 审查中心 / 回收站 / 审计日志 / 设置（明细见 §7）
- **M4 内置对话**：桌面端自带会话，档案常驻注入 + AI 写操作确认卡 + 本地模型切换
- **M5 可选云同步**：端到端加密同步、多端
